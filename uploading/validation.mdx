An upload is checked twice. The API checks the request immediately. The data is checked later, during processing.

## Request checks

These errors are returned immediately with status `400`:

| Problem | Fix |
|---|---|
| The manifest is not correctly formatted | Give every entry `sourceName`, `dataType` (`String`, `Decimal`, or `Date`), and a boolean `isEntity`. |
| The columns are not initialized | [Initialize the columns](/uploading/overview#before-the-first-upload) or send a manifest. |
| The `data` field is missing | Send the file in the `data` form field. |

## Data checks

If the data is invalid, the process ends with status `Error`, and `statusDescription` explains why. Before you upload, check that:

- <span id="3-the-csv-must-not-be-empty" style={{ scrollMarginTop: "8rem" }} />The file has data rows.
- <span id="1-date-column-must-exist-and-parse" style={{ scrollMarginTop: "8rem" }} />The date column exists, and every date matches your date format.
- <span id="2-all-entity-columns-must-exist" style={{ scrollMarginTop: "8rem" }} /><span id="4-entity-columns-must-not-contain-null-values" style={{ scrollMarginTop: "8rem" }} />All entity columns exist. Empty values in an entity column are filled with `none`.
- <span id="6-column-names-must-be-unique-case-insensitive" style={{ scrollMarginTop: "8rem" }} />Column names are unique, even if you ignore case, accents, spaces, and question marks.
- <span id="7-no-duplicate-rows-by-entity-key" style={{ scrollMarginTop: "8rem" }} />No two rows have the same date and entity values.
- <span id="5-new-columns-require-explicit-opt-in" style={{ scrollMarginTop: "8rem" }} />You set `acceptNewColumns=true` if the file adds columns with data to a dataset that already has data.
- <span id="8-short-integer-values-must-fit-int16" style={{ scrollMarginTop: "8rem" }} /><span id="9-decimal-columns-need-≥80%-numeric-content" style={{ scrollMarginTop: "8rem" }} />Numeric columns contain numbers, without thousands separators. Otherwise, values can be read differently, become empty, or turn the column into text. See [number columns](/uploading/manifest#number-columns). Check the result after you upload.

### Error messages

Look for these messages in `statusDescription`. Words in angle brackets stand for your own names and values.

| Message | What to do |
|---|---|
| `Data has not Date column` | Add the date column, or fix its name. |
| `Date should be formatted as <format>` | Make the dates match your [date format](/uploading/manifest#the-date-column). |
| `Data has not required '<column>' column. If you need to change entities, please specify new entitiesColumnNames during upload` | Add the entity column. To change the entity columns on purpose, send a new [manifest](/uploading/manifest). First read the warning about removing an entity column under [upload modes](#upload-modes). |
| `Data is empty` | Upload a file with at least one data row. |
| `Unknown column(s): <columns>. Missing column(s): <columns> - consider renaming to original names or add 'AcceptNewColumn' parameter to confirm adding new column(s)` | Use the original column names. To add the new columns on purpose, send `acceptNewColumns=true`. |
| `Unknown column(s): <columns>. You may use 'AcceptNewColumn' parameter to confirm adding new column(s)` | To add the columns, send `acceptNewColumns=true`. Otherwise, remove them from the file. |
| `Duplicated columns: <columns>` | Rename the columns so that they differ in more than case, accents, spaces, or question marks. |
| `<count> rows are duplicated. First 10 rows as example: <rows>` | Keep one row for each combination of date and entity values, or add an entity column that tells the rows apart. |

Where a message says `AcceptNewColumn`, use the query parameter `acceptNewColumns`.

## Upload modes

Three query parameters control how the file is merged with the existing data.

| Parameter | When `false` or omitted | When `true` |
|---|---|---|
| `onConflictUpdateDB` | If a value already exists for the same date and entities, the existing value is kept. | The value in the file replaces it. |
| `deleteMissingFromDB` | Existing data that is not in the file is kept. | Existing data that is not in the file is deleted. |
| `acceptNewColumns` | The file should only contain known columns. | The file can add new columns. |

<Warning>
  `deleteMissingFromDB=true` permanently removes data. Use it only when the file contains everything you want to keep.
</Warning>

<Warning>
  If you send a new manifest that removes an entity column, Alphacast does not merge the data. The file replaces the whole dataset, whatever the flags say.
</Warning>

Some datasets have a locked manifest. For them, a new manifest, `deleteMissingFromDB`, and `acceptNewColumns` are ignored.

If the file and the upload settings are identical to the last successful upload, nothing changes.

<span id="how-the-three-flags-combine" style={{ scrollMarginTop: "8rem" }} />

## Common combinations

| Goal | `onConflictUpdateDB` | `deleteMissingFromDB` |
|---|---|---|
| Add new data and keep existing values | `false` | `false` |
| Add new data and apply revisions | `true` | `false` |
| Make the dataset match the file | `true` | `true` |

## Check the result

Read the [upload process](/api/datasets/upload#check-an-upload-process). When it finishes, `status` is `Processed` or `Error`. Read `statusDescription` for details, then [download the data](/api/datasets/data) to confirm the result.

For a `Processed` upload, `statusDescription` can include these messages. `<n>` stands for a number.

| Message | Meaning |
|---|---|
| `<n> values added to database.` | Reports what the upload added. |
| `<n> values had conflict and were updated.` | Existing values were replaced because `onConflictUpdateDB` is `true`. |
| `<n> values had conflict but were not updated.` | The file had different values. The existing values were kept. |
| `<n> values where missing in data, and were deleted from database.` | Data that was not in the file was deleted because `deleteMissingFromDB` is `true`. |
| `<n> values where missing in data, but left in database.` | Data that was not in the file was kept. |
| `<n> historical rows outside date range were preserved without comparison.` | Rows dated before or after the dates in your file were kept as they were. |
| `Dataset has not changed. Avoiding csv version upload.` | Nothing changed, so no new data version was saved. |
| `Data content or processing parameters are identical to last successful upload. No changes made.` | The upload repeats the last successful one. |
| `<n> entities were dropped in new manifest, so no merge is possible. Uploading new dataset as final dataset.` | Your new manifest removed entity columns, so the file replaced the whole dataset. |

<span id="what’s-next" style={{ scrollMarginTop: "8rem" }} />

If `onConflictUpdateDB` is `true` and more than 10% of the values changed, `statusDescription` also has a `WARNING`. Check that the file is correct.
